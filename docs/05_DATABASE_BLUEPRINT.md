# 05 — Database Blueprint

**Status:** Phase 6 consolidated  
**Scope:** MySQL database foundation and persistence rules  
**Authoritative decisions:** Phase 6 Q351–Q390 and related locked architectural decisions

---

## 1. Purpose

This document defines the SPMS relational database conventions and persistence rules.

The database must preserve:

- relational integrity
- historical truth
- source and measurement context
- data nature
- data status/freshness
- quality
- provenance
- confidence and uncertainty
- lifecycle state
- temporal context
- authorization boundaries
- reproducibility of analytical results

The database is a persistence layer. It is not the owner of frontend presentation or AI-generated wording.

---

## 2. Database Technology

- Database: MySQL
- SQL: prefer portable SQL where practical
- MySQL-specific features are allowed when justified
- Access layer: PHP PDO
- Queries: prepared statements
- Schema changes: version-controlled SQL migrations

---

## 3. Naming Conventions

Use:

- `snake_case`
- plural table names
- explicit primary keys
- explicit foreign keys where authoritative
- explicit nullability
- intentional unique constraints
- intentional indexes

Formatted UI strings must not be stored as substitutes for semantic values.

---

## 4. Identifier Rules

Internal identifiers are generated by the backend/database according to the domain/table strategy selected during implementation.

Identifiers should not expose unnecessary internal structure.

Public/API references, where needed, are controlled separately from internal identifiers.

---

## 5. Relational Integrity

Foreign keys should be used where they represent authoritative relationships.

The database must prevent invalid orphan relationships where appropriate.

Delete behavior is domain-specific.

Unrestricted cascading deletes must not be used where they could destroy required historical meaning.

Soft deletion/lifecycle states are used where required.

---

## 6. Historical Truth

Meaningful historical analytical records are immutable.

Historical predictions must retain enough context to explain what was produced at the time.

A later model must not silently rewrite an earlier prediction.

Historical records may retain:

- value
- period
- horizon
- resolution
- model/version
- confidence
- uncertainty
- data nature
- status
- provenance
- quality
- calculation/context information

---

## 7. Semantic Data Fields

Where relevant, persisted analytical/data records distinguish:

### Data nature

```text
ACTUAL
PREDICTED
ESTIMATED
SIMULATED
```

### Data status

```text
FRESH
STALE
DEGRADED
UNAVAILABLE
```

Nature and status are separate concepts.

Additional semantic identifiers may be used for domain-specific meanings.

---

## 8. Provenance

Relevant records preserve provenance and measurement context.

Depending on the domain, provenance can include:

- source
- source/provider identifier
- source measurement timestamp
- SPMS ingestion timestamp
- processing context
- transformation
- model/version
- lineage

Sensitive provider credentials are never stored as ordinary analytical provenance.

---

## 9. Data Quality

Data quality is persisted or propagated where required.

Quality may represent:

- reliability
- freshness
- completeness
- plausibility
- consistency
- verification
- source/context suitability

Quality limitations must remain available to downstream analytical and recommendation capabilities.

---

## 10. Confidence and Uncertainty

Predictions and other applicable analytical results may persist:

- stable confidence level
- validated confidence measure
- uncertainty interval/range
- contextual confidence information

Confidence represents evidence/model-supported reliability.

It is not a frontend decoration.

---

## 11. Energy Values

Energy quantities are stored canonically with explicit semantic units.

The database stores numeric values, not formatted presentation strings.

Examples of presentation such as `1,245.50 kWh` belong to the UI/report layer.

---

## 12. Monetary Values

Monetary values use fixed-precision decimal storage.

Currency is part of monetary context.

Do not store currency-formatted strings as authoritative monetary values.

Fixed charges retain their distinct meaning and must not automatically be treated as proportional to energy consumption.

---

## 13. Temporal Rules

Canonical timestamps use UTC.

Household timezone is stored explicitly.

Where provider measurements are involved, preserve provider/source measurement time separately from SPMS ingestion time when required.

Late and out-of-order records must be handled deliberately rather than silently reordered into false truth.

Timestamp plausibility and timezone consistency must be validated.

---

## 14. Nullability and Missing Meaning

NULL must have documented semantic meaning.

Where necessary, distinguish:

```text
NOT PROVIDED
NOT AVAILABLE
NOT APPLICABLE
NOT YET CALCULATED
```

These meanings should not be collapsed into arbitrary numeric defaults.

---

## 15. Uniqueness and Idempotency

Database unique constraints should protect relationships and records where appropriate.

GoodWe ingestion requires source/context identifiers or equivalent deduplication mechanisms.

Application-level idempotency complements database uniqueness where duplicate execution could cause harmful effects.

---

## 16. Indexing

Indexes are designed from actual access patterns.

Likely important access patterns include:

- household-scoped queries
- solar plant + timestamp
- time-range analytics
- historical prediction retrieval
- operational job lookup
- provenance/context lookup where justified

Indexes must be intentional rather than added indiscriminately.

---

## 17. Query Boundaries

Backend queries must use validated:

- date ranges
- pagination
- limits
- filter parameters
- supported sorting

The database must not be exposed as an unrestricted query surface.

---

## 18. Transactions

Application/service operations define transaction boundaries.

Atomic multi-step business operations use transactions.

If an atomic operation fails:

```text
BEGIN
 ↓
Business Changes
 ↓
Failure
 ↓
ROLLBACK
```

Partial authoritative state must not be presented as completed.

---

## 19. Concurrency

Meaningful concurrent changes use optimistic concurrency/version/context validation.

Where appropriate, records may use:

- `version`
- `revision`
- `updated_at`

or an equivalent mechanism.

Silent last-write-wins behavior is not acceptable for important concurrent changes.

---

## 20. Migrations

All schema changes are version-controlled.

Migration files are applied in a controlled order.

Rollback/recovery is used where safe and practical.

Database schema evolution must remain reproducible across environments.

---

## 21. Backup and Recovery

Backups are scheduled.

Backup storage is protected and separate from ordinary application storage.

Recovery requires:

```text
Backup
 ↓
Restore
 ↓
Integrity Validation
 ↓
Reconciliation
 ↓
Health Verification
 ↓
Recovery Complete
```

A backup existing is not sufficient proof of recoverability.

---

## 22. Core Principle

> The SPMS database must preserve relational integrity, historical meaning, provenance, quality, confidence, temporal context, and lifecycle state without becoming a second presentation layer or silently changing authoritative truth.
